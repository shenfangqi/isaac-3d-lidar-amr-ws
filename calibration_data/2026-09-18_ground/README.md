## `0.10 m/s` 前进距离异常的源码初查

- 检查 ESP32 固件提交 `068071e`：前后方向共用同一 PCNT 四倍频硬件计数器、
  `int64` 累计路径和 `1560 counts/rev` 常量；未发现前进方向专用的约 10% 比例
  分支。
- PCNT 使用 `accum_count=true`、`±1000` watch point 和 `1 us` glitch filter；
  本次累计约 1.1 万 ticks 不会造成软件整数溢出，且 PCNT 输入速率远低于硬件
  极限。
- 现有证据尚不能区分“前进较高转速下方向相关漏边沿/信号质量问题”和“现场
  前进距离测量系统偏差”。在示波器/逻辑分析仪或 LiDAR/视觉外部轨迹真值可用
  前，不修改编码器 CPR、轮半径或固件计数逻辑。

## MID-360 上电、网络和静态 IMU 验证

- MID-360 使用稳压 `12 V / 2 A` 电源独立供电，Jetson 无需关机；本轮没有发布
  任何 `/cmd_vel`，车辆保持静止。
- Jetson `enP8p1s0` 为 `192.168.2.100/24`，MID-360 为
  `192.168.2.202`；链路 `100 Mb/s` 全双工，3 次 ping 零丢包，平均约
  `0.787 ms`。
- Livox ROS Driver 2 `1.2.7` 成功发布 `/livox/lidar` 和 `/livox/imu`；直接
  测得点云约 `10.00 Hz`、IMU 约 `200 Hz`，点云每帧约
  `19680--20160` 点。60 秒采样期间有线网口 `errors/dropped/missed=0/0/0`，
  驱动日志无错误。
- 旧 `health_check.py` 使用单线程 `spin_once` 同时反序列化点云和 IMU，只能
  消费约 `4.7 Hz`；这是监测脚本瓶颈，不能解释为传感器降频。权威频率取独立
  `ros2 topic hz` 结果。
- 静止收集 1849 个连续 IMU 样本，ROS header 时间覆盖约 `9.2405 s`，平均
  正间隔约 `5.0003 ms`、最大约 `7.8301 ms`、无非递增时间戳。平均陀螺仪为
  `(0.00301, -0.00340, -0.00234) rad/s`；平均加速度为
  `(0.00964, -0.00944, 0.99177) g`，方向表明传感器约为 `+Z` 向上，静态
  roll/pitch 仅约半度。最终外参仍需用点云平面和机械测量确认。
- Livox 驱动源码明确声明加速度输入单位为 `g`，但原样写入
  `sensor_msgs/Imu.linear_acceleration`；同时输出单位四元数和全零姿态协方差，
  不应直接交给通用 ROS 融合器。新增 `carbot_hardware/mid360_imu_adapter`：将
  加速度乘以标准重力 `9.80665`，发布 `/mid360/imu/data_raw`，保留陀螺仪
  `rad/s`，并以 `orientation_covariance[0] = -1` 标记无姿态估计。
- Jetson 干净构建成功，8 项 `carbot_hardware` 测试通过；实时输出约
  `199.9 Hz`，静止样本 Z 加速度约 `9.50 m/s^2`，单位和不可用姿态标记均
  验证通过。尚未启用任何定位融合。
- 标准 PointCloud2 累计 12 帧、约 24 万点。排除距雷达 `0.6 m` 内的车体遮挡
  后，木地板主平面含 1537 个内点，拟合得到原点离地约 `0.20658 m`、地面法向
  对应 roll/pitch 约 `-0.795/-0.182°`；内点残差标准差约 `5.65 mm`、95% 绝对
  残差约 `9.72 mm`。较早的宽范围拟合得到约 `0.061 m` 平面，已识别为车体
  自遮挡面，不作为地面证据。
- 常驻服务运行后又用 Livox CustomMsg 连续采集 36 帧，分成三批独立拟合：
  原点高度约 `0.20115/0.20260/0.20150 m`，批间跨度 `1.45 mm`；地面法向对应
  roll 约 `-0.689/-0.432/-0.549°`、pitch 约
  `-0.374/-0.336/-0.336°`。重复性支持“约半度静态倾斜”的观察，但绝对高度
  与先前 PointCloud2 拟合仍有约 `5 mm` 算法/采样差异，因此机械尺寸推导的
  `0.209 m` 继续作为几何基线。
- 上述 CustomMsg 仅用于本轮原始标定复核。正式常驻服务随后切换为 Livox 原生
  `sensor_msgs/msg/PointCloud2`，保留每点 timestamp，并与仿真和定位/建图消费者
  的 `/livox/lidar` 接口统一。
- 地板法向包含地板坡度、左右履带支撑差和整车相对重力的静态姿态，不能仅凭
  这组数据分离出雷达相对 `base_link` 的支架误差；没有把约半度结果写入固定
  RPY，继续保留 nominal `[0, 0, 0]`，等待车体基准面或已知墙面的外部约束。
- 官方机械图给出 MID-360 外壳总高 `60 mm`、坐标原点 O 位于底面上方
  `47 mm`。结合外壳顶面离地实测 `222 mm`，O 的机械尺寸推导高度为
  `222-60+47=209 mm`；与点云地板拟合相差约 `2.4 mm`。据此采用 O 离地
  `0.209 m`、相对 `base_link` Z 为 `0.119 m` 的几何基线，并将 RTX、
  `livox_frame` 和 `front_3d_lidar` 相对外壳底面统一为 `+0.047 m`。
- 实车 M12 航空插头朝向车尾；MID-360 官方顶视坐标图中插头位于传感器
  `-X` 侧，因此传感器 `+X` 朝车头，名义 yaw 确认为 `0 rad`。这项观察可以
  排除 90°/180° 方向错误，但不能给出亚度级安装误差；最终 XY、精密 RPY 和
  IMU 内部杠杆臂仍需验证。
- 另取 1000 个 IMU 样本比较 Jetson 接收时钟与 ROS header：平均差约
  `0.811 ms`、95% 约 `0.984 ms`、最大约 `6.091 ms`。但 Livox 驱动源码表明，
  数据未标记为 PTP/GPS 同步时会丢弃传感器时间并使用主机当前时间；Jetson
  `ptp4l`、`phc2sys` 均未运行，`enP8p1s0` 也没有硬件 PTP 时钟。因此这些数字
  只证明主机接收重打时间较稳定，不能证明 MID-360 硬件时钟同步，融合时间门禁
  仍未通过。

## MID-360 单实例常驻服务

- 新增 `mid360_stack.launch.py`，在同一个 launch 内启动
  `livox_ros_driver2_node` 和 `mid360_imu_adapter`；新增 Jetson 用户服务
  `carbot-mid360.service`，显式设置 Livox SDK `LD_LIBRARY_PATH`，并用 systemd
  cgroup 统一管理子进程。
- 服务部署后为 enabled/active。主动重启前后，旧驱动/适配器 PID 均退出并由
  各一个新 PID 替换；`/livox/lidar`、`/livox/imu`、
  `/mid360/imu/data_raw` 的发布者数量均为 1。点云约 `9.99 Hz`，SI IMU
  约 `200 Hz`。
- `carbot-wheel-odometry.service` 在部署和重启过程中始终 active；没有发送
  `/cmd_vel`。
- Jetson 用户 linger 为 `no`：服务会在用户登录会话中自动启动，但不能保证在
  无用户登录时启动。若最终要求开机即采集，需要管理员启用 linger 或改为系统级
  service。
- 已安装 `linuxptp 3.1.1`，新增并启用系统服务
  `carbot-mid360-ptp.service`：仅绑定雷达专网 `enP8p1s0`，使用 UDP/IPv4、
  E2E 和软件时间戳，并强制 Jetson 为唯一 PTP 主时钟；该网卡没有硬件 PTP
  clock，因此不运行 `phc2sys`。服务重启后端口稳定进入 `MASTER`。
- 为避免仅凭 ROS header 推断，短暂停止 Livox 驱动并直接读取雷达 UDP 协议头：
  点云包 `200/200`、IMU 包 `200/200` 的 `time_type` 均为 `1`，确认 MID-360
  已切换到 PTP 设备时间。恢复服务后三个传感器话题均只有一个发布者，点云约
  `10.00 Hz`、原始和 SI IMU 均约 `200 Hz`。
- PTP 锁定后的 1000 个 IMU 样本无时间戳倒退；稳态主机接收时间减设备时间戳
  的中位数约 `0.965 ms`、95% 约 `1.335 ms`。订阅建立时出现一次约 `144 ms`
  的 DDS 队列积压，未计作稳态链路延迟。MID-360 到 Jetson 的时间同步门禁通过；
  与 ESP32 轮速流的跨传感器时间关系仍需单独验收。

## MID-360 与 ESP32 轮速的跨传感器时间

- 静态同时采集得到 403 个轮速样本和 1146 个 MID-360 IMU 样本；ESP32 状态为
  `time_synchronized=true`。轮速 header 增量与 `device_stamp_us` 增量完全一致，
  除一个已知重复帧外均单调；说明 header 表示 ESP32 采样时间，而不是 Jetson
  收包时间。
- 当前长 session 中，轮速“Jetson 接收时刻减 header”中位数约 `64.84 ms`、
  95% 约 `74.96 ms`；同次测量的 MID-360 PTP IMU 分别约 `1.87/2.57 ms`。
- 复查此前 30 分钟静态 bag 的 89950 个轮速样本：逐分钟中位延迟从第 0 分钟
  `8.76 ms` 下降到第 18 分钟 `1.98 ms`，再升到第 29 分钟 `19.01 ms`；并非
  一个可用固定常数补偿的链路延迟。
- 固件提交 `068071e` 的 `ros_time.c`/`ros_executor.c` 表明：只在 micro-ROS
  session 创建时调用一次 `rmw_uros_sync_session()`，随后始终应用同一个 epoch
  offset。该设计无法持续跟踪 ESP32 晶振漂移或 Jetson 系统时钟校正。固件需
  增加周期重同步，并对 offset 平滑/限幅以保证发布 header 严格不倒退；完成和
  长时复测前，不把 ESP32 轮速与 MID-360 IMU 的跨传感器时间门禁标为通过。

## 2026-09-19 双网卡 DDS 与真实 nvblox 静止建图

- Jetson 固定使用 `wlP1p1s0=192.168.1.109/24` 和
  `enP8p1s0=192.168.2.100/24`；Wi-Fi NetworkManager 配置已持久禁用 power save。
  真机工作站容器统一使用 Fast DDS。清除重复测试订阅后，未传点云时 Ping 平均
  约 `3.6 ms`，`odom -> livox_frame` 可连续取得。
- 原始 `/livox/lidar` 每帧约 19968--20064 点、`point_step=26`，可靠 DDS 经
  2.4 GHz Wi-Fi 单订阅仅约 `3.8 Hz`，并造成 TF 饥饿。该结果否定了直接跨 Wi-Fi
  传原始 Livox PointCloud2 的移动建图方案。
- Jetson 新增 `/mid360/points_xyz`：只保留 XYZ，Best Effort QoS，并以轮换
  stride 4 均匀抽取。实测一帧 4992 点、`point_step=12`、59904 bytes，速率
  `10.03 Hz`；原始话题保持不变，供 Jetson 本机算法使用。
- nvblox 真机配置使用系统时间、`global_frame=odom`、`pose_frame=livox_frame`、
  `input_qos=SENSOR_DATA`。实测真实回波俯仰边界约 `-7.95--+54.04°`，FOV 容差
  配置为 `-10--+55°` 后不再触发整帧拒绝。
- 静止车体生成 `152 x 56`、分辨率 `0.05 m` 的非空 OccupancyGrid；代表帧包含
  4258 unknown、3003 free、1251 occupied，发布约 `9.83 Hz`。建图持续期间
  TF 连续可用，30 次 Ping 零丢包、平均约 `36.6 ms`。本次未发布 `/cmd_vel`；
  移动建图、地图几何精度、闭环定位和 Jetson 本机 nvblox 部署仍待后续验证。
